# 0056: A link slot's entries may be loaded from a module's API, and the footer has a menu

- **Status:** Decided; applied in `pages`' PR. The owner chose header and footer menus on 2026-11-21 (recommended was the footer alone), so the slots take links a module loads (`dev plans/contracts/pages.md`, §2 and §8, 4).
- **Context:** A module's slot entries were fixed when its binding was built: `defineModule({ slots: { "nav.public": [{ label, to }] } })`. A page's place in a menu is a row the site's people choose, so `pages` can't name its links ahead of time. The footer had only `site.footer`, which holds parts, not links, so a site's own footer had nowhere to put a menu that modules fill.
- **Decision:**
  1. **Loaded links.** A binding may give a loader for any link slot, `defineModule({ links: { "nav.public": load } })`, where `load` answers that slot's entries (`LinkEntry[]`, or `AdminLinkEntry[]` for `nav.admin`). `useSlot` runs each loader through TanStack Query (`["kernel", "slot-links", <module>, <slot>]`) while its module is on, and each new page reads again those over a minute old (the frame keeps its menus drawn, so freshness alone would wait for the window's next focus; Codex on #121), and puts what it answers after the module's fixed entries, so `useSlot` and `SlotOutlet` give them unchanged, a permission on one hiding it as on a fixed one. Until a load answers, and if it fails, the module gives only its fixed entries; the rest are unchanged. A loaded link is checked as a fixed one is when the binding is built, a path on this site and, for `nav.admin`, under `/admin`; one that isn't is left out, with a warning in the console.
  2. **`nav.footer`,** a link slot for the footer's menu. The frame's own footer draws it in a `<nav aria-label="Footer">`, before `site.footer`'s parts, and only while it has entries; the frame's header draws `nav.public` as before. A site with its own footer places it with `SlotOutlet`, as it places `nav.public` in its own header.
  3. `pages` is the first to load: `nav.public` from `GET /api/pages/menu?place=header` and `nav.footer` from `?place=footer`, each the live pages the editors put in that menu, in their order.
- **Rejected:**
  - A kernel table of menus, or a `menus` module: what's in a menu is each page's own setting (VybeSite's `in_menu`), and another table would have to follow every page's address and state.
  - A part in `site.footer` that draws `pages`' links: the header holds no parts, and a site's own header and footer couldn't place the links where their design puts them.
  - Loading every menu before the app's first render: a menu would hold up every page.
- **Consequences:** A visitor's moves between pages ask each loader once a minute at most, from TanStack Query's cache. The manifest schema's `slots` gains `nav.footer`. A site that draws its own footer adds `SlotOutlet name="nav.footer"` to it, or its footer menu doesn't show: a note for VM Website.
