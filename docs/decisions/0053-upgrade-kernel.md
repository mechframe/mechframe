# 0053: `mechframe upgrade kernel`: the new copy from a Git ref, the base from the lock's commit, whole or not at all

- **Date:** 2026-11-21
- **Status:** Decided; applied in #111 (contract `dev plans/contracts/mechframe-upgrade.md`, approved by the owner on 2026-11-21 as recommended, its four answers in §8)
- **Context:** A site made with `mechframe new` holds a copy of the kernel and the template, and nothing brought the kernel's later changes into it. Vibrant Mindz needed #101's `color.field`, #105's `line-4` and #106's own header and footer. The push plan's way round was a fresh site with the site's own parts moved across (M3). SPEC 12 had left `diff` and `upgrade` for a module's second version, reading the old copy from a Git tag per version. But the kernel's version stays `0.1.0-dev.0` while it changes daily, so a tag per version can't name what a site got. The upgrade needed:
  - where the new copy comes from, when the checkout may be on another branch;
  - the base, what the site was given, for a three-way comparison;
  - what it does where both sides changed a file;
  - what it does with the template's files, which the lock doesn't hash.
- **Decision:**
  1. **`mechframe upgrade kernel [--site] [--from <ref>] [--base <commit>] [--merged <path>]... [--dry-run]`** reads the new copy from a Git ref of the CLI's own checkout, `main` by default, through Git's objects (`cli/mechframe/gitref.py`), never its working tree. It fetches nothing, so `main` is the checkout's local branch. `upgrade <id>` for a module waits for a module's second version and is refused for now.
  2. **The base is the lock's new `kernel.commit`** (`schema/lock.schema.json`, optional). `new` writes it only when every file it copies, kernel, template, pins and `tokens.css`, is as `HEAD` has it; `upgrade` always writes it. An older lock has none. Its candidates are the commits on `--from`'s history whose kernel files hash to every one in the lock. If they hold the same template, pins and `tokens.css`, the newest is the base. If they differ, it's refused, naming the first and last, until `--base` names one (Codex on #108: a template-only commit mustn't pass for a site edit). `--base` must hold the lock's kernel.
  3. **Each file three ways, as the contract's table has it:** the lock's hash or the base's copy (L), the site's file (S), the new copy (N). S = L takes N; only the site's change keeps the site's; S = N writes nothing; new in N lands unless the site has a file there; gone from N goes unless the site edited it; missing from the site stays missing unless N changed it. Every other case is a conflict.
  4. **Whole or not at all.** With any conflict, nothing in the site changes but `.mechframe/upgrade/`: a unified diff per conflict, the base to N, and `README.txt` with the command to run again. The command exits 1. `--merged <path>` keeps the site's file as its edit on the new copy, and the lock takes N's hash. It may name any file the upgrade compares: one the merge settled outright (the new copy taken whole, or a file the kernel removed deleted) is no longer a conflict and follows the table (Codex on #111). A path the upgrade doesn't compare is refused. The lock is read inside the run's hold on the site (Codex on #111). With no conflict left, every file is written through `add`'s journal, so a failure half-way puts each back; the lock takes N's hashes, version, spec and commit, and `.mechframe/upgrade/` goes.
  5. **The template's files follow the same rule,** their base the base commit's copy with the site's name and theme written in (`new.written_in`). This covers `templates/site/`, the pins and the lock's theme's `tokens.css`. The site's own are never touched: `backend/app/site/`, `web/src/site/`, the two registries, `.env.example` and `.railway/railway.ts`. The site's name comes from `.env.example`'s `SITE_NAME`, as `new` wrote it. Without it, a file that carries the name is kept and listed as not compared. The kernel's new settings are the keys new in the template's `.env.example`, printed to add by hand, since `kernel.json` lists none.
  6. **A run holds the site by `.mechframe-busy`,** as `add` and `remove` do, so none of the three overlap. It prints the next steps for the site's own Python: `pip install` when the pins changed, `npm ci` when the web package did, then the migrations (decision 0049 stands), the tests and `mechframe check`. The template's `.gitignore` leaves out `.mechframe/`.
- **Alternatives:**
  - The base kept in the site (`.mechframe/base/`): no Git needed, but the kernel twice in every site (§8 question 1).
  - Write the clean files and leave conflict markers in the rest, like `git merge-file`: the site wouldn't build until they're cleared (question 2).
  - Upgrade only the kernel's copy, printing the template's changes: Vibrant Mindz's `tokens.css` would still be copied by hand (question 3).
  - The newest commit matching an older lock's kernel: wrong whenever a template-only commit follows (Codex on #108).
- **Consequences:**
  - A site takes the kernel's changes with one command. Its own edits stay visible to `mechframe check` as edits on the new copy.
  - The CLI now needs Git and a clone for `upgrade` (not for the other commands). A shallow clone without the lock's commit is refused, naming it.
  - Sites made before this have no `kernel.commit`: their first upgrade finds the base, or asks for it. Checked live on 2026-11-21: a site made with `32a8751`'s own CLI found its base by its hashes and took `origin/main`'s kernel (`69bd37a`, hook 6 in), 2 files added and 18 written, then `mechframe check` passed.
  - The lock's schema refuses unknown fields, so a checkout from before this refuses a lock that has `kernel.commit`: run the CLI from a checkout at or after it.
  - A module's upgrade can reuse `judge`, the diffs and `--merged` once a module ships its second version; its lock entry will want a commit too.
