# 0040: The kernel's admin shell is built to the Vibrant Mindz canvas design, styled by tokens

- **Date:** 2026-11-17
- **Status:** Decided; applied in K4. Amends 0008's "the admin shell is VybeSite's, as it stands" (SPEC Q11). Amended 2026-11-25: the admin's form parts, then its lists' and dashboard's parts, follow the boards (below).
- **Context:** The owner's rule for the Vibrant Mindz site (2026-11-17, through the VM Website session): its admin must look exactly like the canvas **Admin** page, as its public site must look exactly like its boards. The boards are `VM Website/design/site/Admin*.dc.html` (Dashboard, Players, Album, Products, Member, Roles), drawn by `VM Website/design/generators/admin_kit.py` and `build_admin.py`. The brief is `VM Website/design/specs/admin-look.md`. KICKOFF's K4 builds the admin shell before themes, so this had to be decided before K4. Two ways were offered: **A**, build the kernel's admin shell to this design, styled by theme tokens, for every site; **B**, keep VybeSite's shell and let a site replace its frame.
- **Decision** (the owner: "Go with option a and those two conditions"):
  1. **Option A.** K4 builds the kernel's admin shell to the canvas Admin design, styled by theme tokens, as the admin of every DevKit (MechFrame) site. VybeSite's shell supplies behavior to port (accordions, unsaved changes, save conflicts, section history), not its looks.
  2. **Only the generic parts go into the kernel:** the sidebar built from each module's `nav.admin` entries, the top bar, the page header, the owner's "Needs you" list (SPEC 8), cards, tables and forms. Screens that fit only this site (Homepage's Players, Beats) stay with their modules.
  3. **It is checked in both themes,** the site's dark one and the light default (Machined Light), with contrast measured as drawn in each.
- **Alternatives:** *B, a replaceable frame:* two shells to keep looking right, and the kit's parts would have to suit both frames. *VybeSite's shell as it stands (0008):* the site's admin couldn't match its boards.
- **Consequences:** SPEC Q11 changes, with a change-log line. K4's admin shell work starts from the boards and the brief. The Vibrant Mindz mark and palette stay in the site's theme, never in the kernel (the repo is public). The admin and auth screens not drawn yet are designed in the VM Website folder before the step that needs them (the brief lists which). Two related owner rules from the same day: the built site matches the canvas exactly, with no rounding to the theme's scale (`VM Website/design/theme/vibrant-mindz/README.md`, "At K4"), and hosting is Railway, as SPEC already says.
- **Amendment, 2026-11-25: the admin's form parts follow the boards** (the owner, 2026-11-24: "Kit to the boards", after VM Website measured Settings › AI, Writing and a style's page; its ask, `VM Website/dev plans/2026-11-24-admin-forms-kit-ask.md`). Where the kit and the boards' form helpers (`admin_kit.py`: `field`, `select`, `sbtn`, `note`, `notice`, `dialog`, `accordion`, `card`, `h2`) differ, the kit moves, inside the admin only (`.mf-admin-look`). A field's hint goes under its control, after any error, 12px; a label is at 400; a field's text in the font's own line height, and a text box as tall as its rows with no minimum. The select draws the boards' chevron, and one that's off is at 55%. A dialog's and a form card's buttons are the small size, 34px. History and every accordion are radius 12, their title 16px. A warning with nothing to click sits on the canvas's ground, radius 12. A card's description is 14px under its title's line, which keeps the card's button; a card's empty state is a dashed box. A switch row has a rule above it and 12px of room, its name 16px at 400, the switch with no edge, and rows in a list touch. A settings form's card stops at 760px, its parts 18px apart. The member pages keep the kit's order and sizes: their boards draw a field as label, hint, control. Sizes stay fixed in code at the boards' values; colours stay tokens. The older boards draw a card's buttons at 38px (Media, Inbox, a table's rows), so only the settings forms' and the dialogs' buttons are small.
- **Amendment, 2026-11-25, later: the admin's lists and dashboard follow the boards too** (the same "Kit to the boards"; VM Website's asks of 2026-11-25, `2026-11-25-admin-music-ask.md` items 5 and 6, and `2026-11-25-statcard-ask.md`, measured against `admin_kit.pill`, the boards' tables and AdminDashboard's `stat()`). Inside the admin, a pill's words are 12px, the pill still 24px tall, and a table's column heads are 12px, each in the font's own line height. A dashboard card's link is as tall as its words, with no minimum (the card's one target, inside its 20px padding, it keeps WCAG 2.5.8 by its spacing), and its figure is in the font's own line height. The kit's `Table` takes a column marked `rowHeader`: its cell is the row's header (`<th scope="row">`), so a screen reader names the row by it, drawn at 600 as the boards draw a row's name. That option holds everywhere, since a module opts in; where a table sits (a flush card) and which column names its rows stay each module's.
